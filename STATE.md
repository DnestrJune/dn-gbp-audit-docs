## 1. What this is

A Google Business Profile audit tool for small venues in Romania: it fetches a venue's
public profile, reviews and nearby peers, and reports completeness checks, reputation
metrics and risk flags. It is run by an operator to produce a report shown to a venue
owner. It grades nothing and composes no prose — the engine emits ids and values only.

## 5. Known defects

- 71 of the 103 stored audits do not carry `engineVersion` 2, so the version gate at
  `frontend/app/lib/report.ts:106` renders them dark. Measured 2026-08-18: 32 rows at 2,
  16 at 1, 55 with no `engineVersion` in `result_json`. Any share link created before an
  audit was re-run opens a page with no figures on it.
- No source exposes the owner-written description. `descriptionPresent`
  (`src/engine/completeness.ts:56`) reads `na` on all 103 stored audits — checked against
  the D1 rows, not assumed — so completeness is measured over 6 checks and never 7.
- `photos` is deliberately out of the Places field mask (`src/adapters/places.ts:167`)
  and `photoCount` comes only from the crawler's `imagesCount`
  (`src/adapters/crawlerPlaces.ts:216`). A venue the crawler misses therefore has no
  photo figure at all, with no Places fallback behind it.
- `DEFAULT_MAX_REVIEWS = 90` (`src/config/audit.ts:31`) is a spend ceiling, not a sample
  size. A venue with more than 90 reviews inside the 180-day window truncates, and every
  windowed metric, the star spread, the monthly series and the latency bands then
  describe the newest 90 reviews only. The engine marks this `reviewsTruncated`; a
  truncated audit is not fit to send to an owner.
- `newReviewsLast90Days` can never be reliable, so it is null on every stored row.
  `windowedReliability` (`src/engine/reputation.ts:188`) requires
  `reviewWindowDays >= 180`, and `summariseReviews`
  (`src/adapters/apifyReviews.ts:244`) sets that to `min(age of the oldest review
  returned, 180)` — which reaches 180 only when the fetch came back EMPTY, and an empty
  fetch is `noReviews` at `src/engine/reputation.ts:187`. The two conditions exclude each
  other by construction. Measured 2026-08-19 across all 32 `engineVersion` 2 rows: 12
  have a 180-day window and all 12 read 0 reviews; the other 20 read reviews and all have
  a window under 180. The metric is `suppressed` on every audit, and
  the outreach brief NO LONGER EXPOSES IT AT ALL — a permanently-null field in a contract
  read by a composing model is a sentence waiting to be written about it, and
  `test/worker/outreach-brief.test.ts` pins the exact key set of `reviews.analysed` so it
  cannot come back quietly. The metric still appears in the brief's `suppressed` list
  under its own id, which is where a measurement we declined to make belongs. The fix is
  an engine change and a version decision, not a threshold tweak; do not re-add the field
  to the brief before that lands.
- Apify returns owner responses dated before the review they answer — observed 4 of 96 on
  one venue, by up to 613 days (`src/adapters/apifyReviews.ts:156`). The adapter drops the
  date and keeps the reply, so those pairs land in `answeredUndated` and carry no delay
  figure. The reply is real; its timing is not recoverable.
- `PLACE_DETAILS_USD_PER_CALL = 0.025` (`src/config/costs.ts:57`) is the least certain
  number in the file. Published rates disagree between $25 and $40 per 1,000 depending on
  whether our mask's amenity booleans count as Atmosphere fields. Every `placesUsd` figure
  is understated by up to 1.6x if the higher SKU applies. Settling it needs a month of
  Google Cloud billing.
- `distance_m` on a stored lead (`src/worker/leads.ts`) is one figure per lead where the
  quantity is per audit-lead pair: it is measured from the seed of the audit that ran the
  search. The overwrite is stopped — the first audit to see a lead now sets the distance
  and later ones only backfill a NULL — so no value is lost any more, but the column
  still holds a distance from one origin only. Distance ordering on the leads page is
  therefore meaningful within one neighbourhood and not across a city.
- `'food'` is in `dishTokens` (`src/engine/vocabulary.ts:122`) and Google attaches `food`
  to a supermarket's `types`, so `foodServiceVerdict` answers `'yes'` for supermarkets and
  grocery stores. Left in place deliberately: the consequence today is menu wording on the
  fixes list for a venue outside the target segment, not a false claim about the venue.
- `src/strings/ro.ts` is a first-pass translation not reviewed by a native speaker, and
  `frontend/app/lib/strings.ts` was written to the same standard. The key set is complete
  and test-enforced; the wording is not signed off.

## 7. Not to be done

- Do not repair, migrate or partially render a stored audit that fails the version gate.
  The gate is the design: the report says the figures are not shown and stops.
- Do not bump `ENGINE_VERSION` to reflect a code change, a threshold move or a check
  becoming inapplicable. Only a stored record that would now read false earns a bump.
- Do not raise `DEFAULT_MAX_REVIEWS` to make a truncated audit shippable. Reviews are the
  dominant per-audit cost and the cap is a spend ceiling.
- Do not hardcode a Worker URL as the frontend's fallback. An unset
  `NUXT_PUBLIC_WORKER_BASE` must fail on screen.
- Do not run `wrangler deploy` bare; `npm run deploy` is what stamps the commit that
  `/health` reports.
